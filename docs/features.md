# Features — cirrascale-planner

> Team doc. What each feature is and when it counts as done. Anyone can add or
> edit a feature through a PR.

## How this works with Jira

- **One feature = one Jira epic.** The epic key (e.g. `SCRUM-5`) is the
  feature's ID here.
- **This doc holds the spec:** what the feature is, acceptance criteria, and open
  questions or decisions.
- **Jira holds the work:** status, owner, and priority live only on the
  [SCRUM board](https://qualcomm-ai100-travel.atlassian.net/jira/software/projects/SCRUM/boards/1).
  Don't copy them here.
- **Building a feature:** create the stories and subtasks under its epic in
  Jira. Update this doc in the same PR when the spec changes (a criterion added,
  a decision made).

### Adding a feature

1. Create an epic in Jira.
2. Add a row to the [overview](#overview) and copy the [template](#template)
   into [Feature specs](#feature-specs).
3. Open a PR.

## Feature specs

### SCRUM-5: Chat-based trip planning

**What:** The user types a natural-language trip request (e.g. _"beach vacation
for 5 days, relaxed pace, great food"_) and gets a structured, day-by-day
itinerary. They can then refine it with follow-up messages instead of starting
over.

**Acceptance criteria:**

- [ ] The model returns the itinerary as JSON, not free text.
- [ ] The JSON is validated against a schema; invalid output is retried or
      reported as a clear error.
- [ ] The itinerary has the number of days the user asked for, and each day
      lists activities and meals.
- [ ] A follow-up message (e.g. _"make day 3 more relaxed"_) updates the
      current itinerary instead of generating a new one.

**Notes / open questions:**

- Exact schema fields (activity times, costs, locations?) to be agreed.
- The current `/api/plan` route returns Markdown; this feature moves it to JSON.

---

### SCRUM-6: Saved preferences

**What:** Store a client's preferences (pace, budget, interests, dietary,
accessibility and transit needs) and past trips, and use them to personalize
new itineraries through embeddings and retrieval.

**Acceptance criteria:**

- [ ] Preferences, including accessibility and transit needs, can be saved per
      client.
- [ ] Demo clients and past trips exist as synthetic data (no real personal
      data).
- [ ] Preferences and past trips are embedded; the most relevant ones are
      retrieved and included when generating an itinerary.
- [ ] For the same prompt, two clients with different preferences get
      noticeably different plans.

**Notes / open questions:**

- Vector store choice is open (Qdrant is being evaluated in SCRUM-36).
- Depends on SCRUM-5.

---

### SCRUM-7: Visual itinerary

**What:** Show the trip as a visual timeline with a generated image for each
day or activity, and let the user export or share it.

**Acceptance criteria:**

- [ ] Images are generated by an image model on Cirrascale.
- [ ] Image prompts are built from the validated itinerary, not raw user text.
- [ ] The timeline shows each day (or activity) with its image.
- [ ] A failed image doesn't break the view (placeholder shown instead).

**Notes / open questions:**

- One image per day or per activity? Per activity is slower and uses more quota.
- Image model choice is tracked in SCRUM-45.
- Export/print and sharing (SCRUM-18, SCRUM-19) need their own criteria.
- Depends on SCRUM-5.
